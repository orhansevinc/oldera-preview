## Why runs #23/#24 did not pass

Run #24 had already proved the real chain through character create/select, wire zone `21`, native zone `210`, and Moradon assets loaded. The failure occurred because the WS10 driver armed the world proof around synchronous client preload and then allowed only a fixed 60-second marker wait. The genuine `KnightOnLine.data` generated by this path is `615930538` bytes (~587 MiB), so the browser can remain in long synchronous native/resource work before the first completed Moradon render evidence.

This was treated as a WS10 harness timing/observation issue rather than a provider defect.

## WS10-only fix

The final harness:

1. uses a `600000 ms` world-phase deadline instead of a fixed 60-second wait;
2. observes console markers from the Node side with 15-second progress heartbeats, avoiding repeated browser-thread `page.evaluate()` polling during synchronous preload;
3. arms request `1010` directly inside the WS10-generated entry page when `Module.print` observes `moradon-assets-loaded`;
4. sets `WS04_CAPTURE_PRESENT_ONLY=1`, so timer fallback cannot read the framebuffer during resource preload;
5. requires actual native `source=present` capture evidence, not merely a READY flag;
6. preserves all terrain, shape, local-player, renderer-error and non-black framebuffer gates.

Run #25 proved this timing policy reaches the real `Present()` and all world markers after the old 60-second boundary. Its only remaining failure was a WS10 matcher that assumed `source=present` immediately followed `ok=1`, while WS04 legitimately emitted size/path metadata between them. Commit `f0cadfb...` validates the capture marker and `source=present` independently; run #26 then passed.
